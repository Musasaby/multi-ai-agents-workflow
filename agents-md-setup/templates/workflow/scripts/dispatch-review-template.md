# レビュー依頼(単発)

これは非対話のワンショット実行です。確認の質問はせず、ただちに以下の手順を実行してください。
コードの変更・コミットはしないこと。書いてよいファイルは `{fix_notes_path}` と理解確認の質問ファイルだけです。

## 対象

- タスク: `{task_id}`(試行 `{attempt}`)
- タスクの定義(`.agents/workflow/tasks.md` の該当節をそのまま):

{task_section}

## 材料

- `git status --porcelain` と `git diff`(未追跡のファイルは中身を読む)
- 子エージェントの完了報告: `{report_path}`

## 手順

### 1. テスト結果の検証

- 完了報告にテストコマンドと結果(全件パス)が明記されているか確認する
- タスクがテストの追加・変更を求めている場合、diff にテストコードが含まれているか確認する
- 報告内容と diff に矛盾がないか確認する(例: 「○○を修正」とあるのに該当ファイルに変更がない)
- 子が「既存エラー」と報告した場合は、そのコマンドを再実行して確かめる(鵜呑みにしない)

報告が欠落・曖昧・矛盾していれば不合格とし、指摘を手順3に含める。

### 2. コードレビュー

受け入れ基準を1項目ずつ diff と照合し、次の観点でも確認する:

- 正しさ: ロジックの誤り、エッジケース、エラーハンドリング
- スコープ: タスク外の無関係な変更が混入していないか
- 規約: AGENTS.md・周辺コードのイディオムとの整合
- セキュリティ: 入力検証、秘密情報のハードコード等

### 3. 判定

判定は **pass / fail の二択**。fail なら、指摘を原因種別(`レビュー指摘` / `テスト報告の不備`)付きで `{fix_notes_path}` に書く(ディレクトリが無ければ作る)。
`fix-notes.md` にはタスク固有の指摘だけを書き、「実装ルール」が定める事項は書かない。pass の場合は `{fix_notes_path}` を書かない。

## 完了報告フォーマット

各項目は1行の値として書く(複数行にしない)。

```
## 完了報告
- Verdict: <pass | fail>
- 指摘: <件数>件(<原因種別。無ければ なし>)
- 要約: <変更内容の1行要約>
- fix-notes: <fail のとき書いた {fix_notes_path}。pass なら なし>
- 理解確認: <作った質問ファイルのパス。作らないなら なし>
```
